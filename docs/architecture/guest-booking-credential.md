# Bookify — Guest Booking Credential

## Module

25.6 — Guest booking credential

## Source of truth

Backend:
merg8511/Bookify.Services.Booking

Frontend:
merg8511/Bookify.Web.Booking

The backend owns booking authorization.

## Backend contract

Anonymous booking creation:

POST /api/v1/bookings

Requires:
Idempotency-Key

Initial successful creation:
HTTP 201 Created

Guest credential response header:
Booking-Guest-Token

The credential:

- Is generated by the backend
- Contains 32 random bytes
- Uses Base64Url without padding
- Is not returned in the JSON response
- Is not recoverable from the database
- Is not reissued on an idempotency replay

The database stores the credential hash.

BookingReference is NOT proof of ownership.

## Access models

Authenticated Customer:
OIDC Bearer token.

Anonymous Guest:
Booking-Guest-Token.

These access models must remain independent.

Guest access does not grant Owner or Admin roles.

## Frontend architecture

Cryptography:

src/lib/auth/guest-credential-crypto.ts

Cookie lifecycle:

src/lib/auth/guest-credential-store.ts

Backend API access:

src/lib/auth/guest-api-access.ts

All three modules are server-only.

## Cookie protection

One cookie per Booking ID.

Development prefix:
bookify-guest-

Production HTTPS prefix:
\_\_Host-bookify-guest-

Attributes:

- HttpOnly
- Secure in Production
- SameSite=Lax
- Path=/
- No Domain attribute

The cookie contains an authenticated encrypted
JWE, not the plaintext guest token.

Encryption:
JWE / dir / A256GCM.

The encrypted payload is bound to its Booking ID
and contains an expiration claim.

## Encryption key

Environment variable:

BOOKIFY_GUEST_COOKIE_KEY

Exactly 32 cryptographically random bytes,
encoded in standard Base64.

Never reuse AUTH_SECRET.

Use independent keys per environment.

All instances of the same environment need
the same encryption key.

Rotating the key without retaining decryption
compatibility invalidates existing guest cookies.

No secret value belongs in Git.

## Retention

Initial technical proposal:
30 days.

This is NOT a backend business rule and does
not alter the server's credential validity.

This policy must be reviewed before production.

When the cookie expires or disappears, the
frontend cannot reconstruct the guest token.

## Initial capture

Module 26.6 will create bookings through
a Server Action or Route Handler.

The creation response must remain server-side.

After a confirmed HTTP 201:

1. Read the real Booking ID from the response.
2. Read Booking-Guest-Token from Response.headers.
3. Encrypt and prepare the guest cookie.
4. Do not serialize the token to the browser.
5. Confirm on a subsequent request that the
   browser retained the cookie.

If the header is missing, do not invent a token.

An authenticated booking may legitimately have
no Guest header.

An idempotency replay does not reissue the token.

Do not automatically create another booking in
an attempt to recover a missing credential.

The caller must preserve the original logical
operation and its Idempotency-Key.

## Access after creation

Use getGuestBookingApiAccess(bookingId).

This provides a server-side API client and
a per-request Booking-Guest-Token header.

It returns null when no valid local credential
is available.

The backend still checks that the token
belongs to the requested Booking.

Never forward the browser's Cookie header
directly to the backend.

Never send Guest credentials as Bearer tokens.

## Local deletion

clearGuestCredential(bookingId) removes the
frontend cookie.

This is local removal only.

It does NOT revoke the backend credential,
cancel a Booking or modify a Payment.

## Recovery limitations

The current backend does not expose a
Guest credential recovery endpoint.

Losing cookies, changing browser/device
or passing the frontend retention period can
result in loss of Guest access.

Do not treat BookingReference, email or phone
as sufficient proof of booking ownership.

Cross-device recovery requires a separately
approved product and backend contract.

## Security constraints

Never expose the raw credential in:

- URLs
- Search parameters
- HTML
- Client Component props
- Browser storage accessible to JavaScript
- Logs
- Analytics
- Error messages
- Telemetry attributes

Do not log raw Response objects containing
sensitive headers.

Do not cache authenticated responses.

Do not automatically retry booking creation
or payment initiation with a new logical key.

Mutating Server Actions and Route Handlers
must preserve their applicable CSRF and
authorization protections.
